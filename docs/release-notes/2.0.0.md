# pg-ledger-mcp 2.0.0

## English

### Summary

2.0.0 replaces the 1.x implementation (DBHub, Node, PostgreSQL functions and triggers, raw SQL tools) with a product written in Java 25 and Spring Boot 4.1. The major version changes because three contracts of the clients change: the form of results, the read tools and the value of `_hostAttestation`. The names and the input keys of the ten write tools and the keys of their results are unchanged. The product is database neutral: a JDBC driver is attached by the user and is not bundled, only ANSI SQL is used and no DBMS-specific feature is used. No list of databases is published. Timestamps are stored and transmitted in UTC.

### Breaking changes

1. **Result wrapping removed.** DBHub wrapped each write result as `rows[0].result`. The keys now stand directly in the result: `status`, `entity`, `id`, `version`, `history_id`, and so on. A client that reads `rows[0].result` must read the keys from the result itself.
2. **Raw SQL tools removed.** `execute_sql_reader` and `search_objects_reader` no longer exist. The twelve structured read tools `ledger_get`, `ledger_defect`, `ledger_task`, `ledger_history`, `ledger_search`, `ledger_defects`, `ledger_tasks`, `ledger_conditions`, `ledger_attention`, `ledger_stats`, `ledger_projects` and `ledger_codes` replace them. Queries that read the schema directly have no equivalent.
3. **The value of `_hostAttestation` changed.** The key is unchanged. A bare `<vendor>:<session-id>` is refused with `ATTESTATION_UNSIGNED`, and a `pgla1` token with `ATTESTATION_VERSION_UNSUPPORTED`. The new value is `pgla2.<author>.<tool>.<request id>.<arguments digest>.<issued at>.<signature>`: an Ed25519 signature that also covers the SHA-256 of the RFC 8785 canonical form of the arguments. Only the new hook jar produces it.
4. **Existing grants need a session key.** `import-legacy` copies the old grants without a key, so a write of an imported author is refused with `ATTESTATION_SIGNATURE_INVALID` until the owner has registered the session key with `key-register`. The grant then works as before.
5. **Imported receipts are not replayed.** A write that repeats the `request_id` of a 1.x request is refused with `REQUEST_ID_LEGACY`; use a new request id.
6. **Settings moved.** The 1.x environment file is gone. Secrets are stored with `secret-set`, and the deploy settings are the Spring Boot properties listed in the README.

### Migration

1. Install the hook jar on every client host first, with a Java 25 runtime on the `PATH`. Writes without a signing hook are refused with `HOST_ATTESTATION_REQUIRED`.
2. Create the two database accounts with the tools of your DBMS, the application account and the DDL account, obtain the JDBC driver
   yourself, and install the 2.0.0 jars with the installer of the host. The 1.x schema stays untouched and is only read. The installer
   stores the secrets (`secret-set`, `token-generate`), registers the driver, creates the schema with `migrate`, applies `dml-grants.sql`
   to the application account and starts the two services. The README (Installation) describes the three targets: a personal PC, a
   Windows server and a Linux server.

```sh
sudo deploy/install.sh --jars=dist --driver-jar=<driver-jar> --driver-class=<driver-class> --owner-account=<ddl-account> --app-account=<app-account> --jdbc-url=<jdbc-url>
```

```bat
deploy\install.cmd dist <winsw-exe> <driver-jar> <driver-class> <ddl-account> <app-account> "<jdbc-url>"
```

3. Migrate on the host of 1.x in this order. Back up the ledger database with the dump tool of your DBMS and copy `/etc/pg-ledger-mcp`
   (the 1.x file `/etc/pg-ledger-mcp/env` holds the 1.x secrets) and the 1.x unit files. Stop the 1.x services yourself
   (`sudo systemctl stop pg-ledger-mcp pg-ledger-mcp-admin` under the default names; the installer stops nothing of 1.x). Create the two
   database accounts, then install with `--from-1x-env=<file>`, which carries the 1.x tokens over before any token is generated, so the
   clients and the admin sign-in keep working; no value is printed, and a secret that exists is kept. The unit files of 1.x that the new
   units replace are kept as `<file>.1x-backup`. Without a terminal, add `--stdin` and give the passwords on standard input.

```sh
sudo deploy/install.sh --jars=dist --driver-jar=<driver-jar> --driver-class=<driver-class> --owner-account=<ddl-account> --app-account=<app-account> --jdbc-url=<jdbc-url> --from-1x-env=/etc/pg-ledger-mcp/env
```

| 1.x environment value | 2.0.0 secret |
|---|---|
| `DBHUB_AUTH_TOKEN` | `ledger.mcp.token`, and the same value as `ledger.admin.agent-token` |
| `PGLEDGER_ADMIN_TOKEN` | `ledger.admin.token`; a 1.0.0 installation had no admin web and has none, then a new one is generated and shown once |
| database password of the ledger logins | `ledger.jdbc.password`, typed by the installer for the application account |

4. Import the 1.x ledger once, on the schema that `migrate` and `setup` made (the state after the installer, which runs `setup`). The import reads the 1.x schema read only, copies everything in one transaction and compares the number of rows and the SHA-256 digest of every table; `--verify-only` repeats only the comparison. It accepts the seed codes and the audit rows that `setup` wrote (a seed code that 1.x also has takes the 1.x values), it refuses when a table of ledger data, a session key or an earlier import is already there, and it lists every value that the new schema cannot hold (an id with whitespace, two ids that differ only in case, a text longer than its column) without writing anything; correct those rows in the 1.x ledger and run it again. The ids of 1.x are kept as they are: an id of a task or a condition is 1 to 120 characters without whitespace or control characters, in any case and with any characters (`:`, `/`, `#`, `.`, `_`, `-` ...), and defect ids keep their form (`<CODE>-D-0001`). Ids of one kind that differ only in case are one id to the new schema (a lookup compares the id exactly, and the key of the id in upper case is unique on every DBMS), so the import refuses such a pair and a task or condition cannot be created with an id that equals an existing one when the case is ignored (`DUPLICATE_KEY`). An empty text of 1.x (`purpose`, `success_condition`, `behavior`, `root_cause` and `condition_text` allowed `''`) is stored as NULL and the tools return an empty string for it, as 1.x did. The `code` of a condition (200 characters) and the `ci_ref` (2000 characters) are longer than in the earlier 2.0 builds, and the `origin_ref` of a task is a long text (up to 20000 characters when written), so every value of 1.x fits. The input keys of the tools are unchanged and no tool schema carries a pattern for an id.

```sh
java -jar ledger-cli.jar secret-set ledger.import.source.password
java -jar ledger-cli.jar import-legacy --owner-account=<ddl-account> --ledger.import.source.url=<jdbc-url> --ledger.import.source.username=<account>
```

5. Every author registers a session key. The session prints its public key and fingerprint, and the owner compares the fingerprint and registers the key on the server it was made for; the grants of that author then work.

```sh
java -jar ledger-client-hook.jar session-key <server> <author>
java -jar ledger-cli.jar key-register <author> <public-key-or-block> <fingerprint>
```

6. Switch the clients: replace the calls of `execute_sql_reader` and `search_objects_reader` by the read tools, and read the keys of a write result from the result itself. Check the server with `mcp-check` and `import-legacy --verify-only`.
7. To go back, stop the 2.0.0 services, copy the `<file>.1x-backup` unit files back (the backup stays), run `sudo systemctl daemon-reload` and start the 1.x services with their previous configuration. The import never changes the 1.x schema. A later run of the installer keeps a backup that equals the unit in place; a backup with other bytes stops `prepare-host` with `HOST_FAILED` naming both files.

### New

- The twelve structured read tools, with `max_rows`, `cursor`, `truncated` and `next_cursor` on the lists.
- `notifications/tools/list_changed`: a change of a common code reaches connected clients without a restart.
- The history keeps the full row as it was before a change (`before_data`, returned with `include_before`).
- Task ids are assigned by the server when none is given.
- One hook jar, `ledger-client-hook.jar`, for Claude Code, Codex and Antigravity (`clients/claude`, `clients/codex`, `clients/antigravity`), with Ed25519 session keys.
- The admin web is server rendered, signs in with the admin token or with OpenID Connect (`ledger.admin.oidc.owners`), and registers the JDBC driver (`ledger.admin.driver-directory`).
- `ledger-cli` with twenty commands, among them `driver-register`, `migrate`, `import-legacy`, `key-register`, `key-revoke`, `mcp-check`, `token-generate`, `secret-import-1x`, `render-deploy`, `prepare-host` and `seal-host`. `secret-set`, `migrate` and `import-legacy` take `--stdin` (the convention of `docker login --password-stdin`: the secret is the first line of standard input, never an argument or an environment value), `secret-set` takes `--if-absent`, `token-generate` takes `--copy-to=<name>`, and `secret-import-1x` moves the two tokens of a 1.x environment file into the secret store.
- `prepare-host` and `seal-host` do in Java what the installers did with operating system commands (`install -d`, `install -m`, `mkdir`, `icacls`, `copy`): the folders with owner and mode or ACL, the copies of the jars, the driver and WinSW, and the hand-over of the secrets to LocalService.
- Two installers that start only what Java cannot do (`useradd`, `runuser`, `systemctl`, WinSW, `sc.exe`, `nginx`) and leave the rest to `ledger-cli`: `deploy/install.sh` (Linux, systemd, optional nginx site) and `deploy\install.cmd` (Windows, services registered with WinSW). They serve a personal PC, a Windows server and a Linux server; macOS is not supported. `--name=<name>` gives an instance of its own: the services are `<name>` and `<name>-admin`, and the Linux user, the directories and the WinSW ids follow the name, so two instances (or an instance next to a host that still runs 1.x) can live on one host with their own ports; Java validates the name before anything is created. Both servers run as one service account that belongs to no person (`pg-ledger-mcp` on Linux, LocalService on Windows), and the secret directory is readable by it alone.
- Two database accounts: the application account, which `migrate --app-account=<account>` gives the least privilege of `dml-grants.sql` (ANSI `GRANT` only, no DDL, no `UPDATE` or `DELETE` on the history), and the DDL account of `migrate --owner-account=<account>`, whose password is typed with hidden input and never stored.
- The settings of an installation live in one directory (`ledger.secrets.home`): `application.yaml` and one file per service, rendered by the installer, and `local.yaml` for your own settings, which is never replaced.
- `token-generate` makes the bearer and admin tokens from 32 bytes of a `SecureRandom` and keeps an existing token on a re-run.
- Schema files `V{n}__*.sql` and the history table `schema_history`, applied by `migrate`; a changed file stops every process at start.
- `setup`, the first setup of the ledger database: it migrates as `migrate` does, checks that the application account can use the schema (exit code `3` and the missing step when it cannot), adds the seed codes that are missing through the service of `code-set` and compares the seed with the database by counts and a SHA-256 digest. Running it again changes nothing. The installers call it.
- The seed bundle `ledger-seed.mv.db` in `ledger-cli.jar`, written by the build from `src/seed/defect-categories.tsv` and `src/seed/install-defaults.properties` (the module `ledger-seed`): the 14 default defect categories and the defaults of an installation. It is H2 data only; the ledger is always kept by the database system that you install, and the registration of an H2 driver or of a JDBC URL of H2 is refused. Only `ledger-cli` carries the H2 driver; the MCP server and the admin web keep none.
- `install-default <name>`: the defaults of an installation (`instance-name`, `mcp-port`, `admin-port`) are written once, in the seed bundle, and `render-deploy`, `prepare-host`, `seal-host`, `mcp-check` and the two installers take them from it.
- Automatic TLS certificates on a Linux server: `tls-issue` and `tls-renew` of `ledger-cli` are a standard ACME client (RFC 8555, HTTP-01, built on the library acme4j, Apache-2.0) that writes `fullchain.pem` and `privkey.pem` (standard PEM) into `/etc/<name>/tls`. `render-deploy` and `prepare-host` take `--tls-acme` in place of `--tls-certificate` and `--tls-key`, with `--acme-directory=<url>` (default: the production directory of Let's Encrypt) and, for the installer, `--acme-email=<address>` and `--agree-tos`. The nginx site then holds a port 80 block for each own host name (the proof, a redirect to https) and the 443 blocks, takes no `default_server`, and a systemd service and timer renew the certificate. The certificate of the operator (`--tls-certificate`, `--tls-key`) is unchanged.
- Deploy settings: `ledger.admin.agent-token` is required and must differ from `ledger.admin.token`; `ledger.admin.lockout.global-delay` slows token checks once many clients fail.

### Changed

- The rules that PostgreSQL functions and triggers enforced (grants, state transitions, same-session refusal, receipts, id assignment, creation provenance) are enforced by the application services with the same error tokens.
- The history has no update or delete path in the application; the grant template of the database module (`dml-grants.sql`) gives the application account no `UPDATE` or `DELETE` on it.
- Times are UTC everywhere; the admin web shows them in the local time of the browser.
- The license changes from the MIT License to the GNU Affero General Public License v3.0 or (at your option) any later version (`AGPL-3.0-or-later`) from 2.0.0; `LICENSE` holds the unmodified GNU AGPL v3 text, and the choice of later versions is stated in the README. `AGPL-3.0-or-later` applies to 2.0.0 and to every release published after it, including any later maintenance release of the 1.x line; the MIT License continues to apply only to the copies already published under it, that is v1.0.0 and v1.1.0. Under section 13, whoever runs a modified version as a network service must offer its users the corresponding source code. The admin web shows a link to the source code in its footer; its address is the setting `ledger.source.url` (default: the public repository of the project), which whoever runs a modified version points at the place where the source of that version is offered.
- The MCP server and the admin web run as one service account and never as root.
- The installers call `setup` where they called `migrate` before. The files that `render-deploy` writes are byte for byte the same for the same options; only the place of the defaults changed.

### Removed

- DBHub, Node and the Node hook scripts, replaced by the Java server, the Java admin web and the hook jar.
- The PostgreSQL functions, triggers and login roles of 1.x; the author and reviewer logins are now the channels of the tools.
- The tools `execute_sql_reader` and `search_objects_reader`.
- The environment file with secrets. The 1.x shell installers, the unit templates and the domain automation of `deploy/` are replaced by the two installers and removed; the history of the repository keeps them.

### Security

- Defect D-0012 is fixed: 1.x did not verify `_hostAttestation`, so a holder of the bearer token could write under the name of another session. The server now verifies an Ed25519 signature made with a key that the owner registered for the author and the server, and checks the tool, the request id, the arguments and the time (`ledger.attestation.window`).
- A signature made for one server never verifies on another, and a missing key is not told apart from a wrong signature.
- The admin web refuses the token of the agents (`AGENT_TOKEN_FORBIDDEN`), limits failed attempts (`ledger.admin.lockout.*`), and uses CSRF tokens and a `Secure`, `SameSite=Strict` session cookie.
- Secrets are read from the secret store with hidden input and are never printed (a token is shown once, by `token-generate --print`, when it is created). The secret directory is owner-only (POSIX permissions, or an ACL on Windows) and readable by the service account alone, which separates the secrets of the ledger from the account of the person and of the agents.
- The database password of the DDL account is typed for one run and is never stored; the application account has no DDL right and no `UPDATE` or `DELETE` on the history.
- The keys of the automatic certificate (`account.key`, `privkey.pem`) are made with the JDK, created owner-only with the protection of the secret store and never printed; the certificate files are replaced atomically, and a failed renewal leaves the old ones. The renewal service runs as the service user without capabilities and writes only its TLS directory and the web root; it reloads nginx with the one fixed command `ExecStartPost=+/usr/bin/systemctl reload nginx`. A challenge token of the certificate authority is written as a file only when it is made of the base64url alphabet.

### Requirements

- A Java 25 runtime on the hosts of the MCP server and the admin web (at a path that every account can execute, not under `/home`, because the service account runs it too; `deploy/install.sh` takes `--java=<path>` and checks it), and on every client host for the hook jar (class file version 69.0; an older JVM refuses it with `UnsupportedClassVersionError`). The build needs JDK 25.
- Linux with systemd, or Windows with the WinSW 2.x executable, which you obtain yourself like the JDBC driver; the installers bundle and download nothing. nginx is needed only for the optional site of a Linux server.
- A JDBC driver of your choice, obtained by you and registered with `driver-register`; the product bundles none. A database whose session time zone is UTC.
- For the automatic certificate: the DNS records of the two host names point to the server, and the ports `80` and `443` reach nginx (a CDN or proxy in front passes `/.well-known/acme-challenge/` through on port `80` without caching or redirecting it, and keeps long connections open).
- The 1.x ledger must be complete up to its last installer step (observed cases, common codes and creation provenance); otherwise `import-legacy` refuses.
- Clock of the client hosts and of the server within `ledger.attestation.window` (five minutes by default).

### Known limitations

- macOS is not supported.
- A text that identifies a row and is empty in the 1.x ledger (the release or the code of a condition, the repository of a fix, a title) is not stored as NULL: `import-legacy` lists it and writes nothing, and the row has to be corrected in the 1.x ledger. The empty texts of the five long text columns are imported (see above).
- `driver-register` writes the registration file even when the schema of the ledger database is not migrated yet (a first installation, or a rerun after the schema was dropped), and says that the row of the owner's audit trail is still to come; `migrate` and `setup` record it, once, when the schema is ready.
- The automatic certificate is for Linux only, because the nginx site is; the commands `tls-issue` and `tls-renew` run on any host with `--webroot` and `--tls-dir`.
- The privilege to use a schema is a statement of the database system and not part of the product SQL: `setup` checks it and stops with exit code `3` when the application account lacks it; an operator gives it, and `setup` continues where it stopped. `setup` never changes a code that exists, so a later version that changes a code of the seed does not change it in an existing ledger; use `code-set` for that.
- `deploy\install.cmd` has no `--stdin` and no `--from-1x-env`: the installation on Windows is interactive, and 1.x ran on Linux only. Creating the operating system user, switching to it, the service managers and `nginx` stay in the scripts because Java has no API for them. Changing the folders needs root, or an elevated prompt on Windows, and there is no probe: Java refuses with `HOST_FAILED`.
- On Windows the secrets are handed over to the service account at the end of the installation, so the owner commands of `ledger-cli` cannot read them afterwards; the owner work is done on the pages of the admin web.
- Another process of the same operating system user can read the session key file; isolation inside one user needs separate accounts.
- A hook that runs with elevated rights is refused (`WRONG_OWNER`); run it as the ordinary user of the host.
- A signed token that is replayed inside the time window can only repeat the same call (receipt idempotency), never carry other content; the window is not a one-time token.
- The MCP server, the admin web and the owner commands share one application account (the service account separates the secrets, not the rights in the database), so a compromised MCP server process holds the right to write the session keys and the grants as well.

## 한국어

### 요약

2.0.0은 1.x 구현(DBHub, Node, PostgreSQL 함수와 트리거, 원시 SQL 도구)을 Java 25와 Spring Boot 4.1로 작성한 제품으로 대체합니다. 클라이언트의 계약 세 가지, 즉 결과의 형식, 읽기 도구, `_hostAttestation`의 값이 바뀌므로 주 버전이 올랐습니다. 쓰기 도구 10종의 이름과 입력 키, 그 결과의 키는 바뀌지 않았습니다. 제품은 데이터베이스에 중립입니다. JDBC 드라이버는 사용자가 붙이며 동봉하지 않고, ANSI SQL만 사용하며 DBMS 고유 기능은 사용하지 않습니다. 데이터베이스 목록은 공개하지 않습니다. 시각은 UTC로 저장하고 전송합니다.

### 호환되지 않는 변경

1. **결과 감싸기 제거.** DBHub는 쓰기 결과를 `rows[0].result`로 감쌌습니다. 이제 키(`status`, `entity`, `id`, `version`, `history_id` 등)가 결과에 바로 들어 있습니다. `rows[0].result`를 읽던 클라이언트는 결과 자체에서 키를 읽어야 합니다.
2. **원시 SQL 도구 제거.** `execute_sql_reader`와 `search_objects_reader`는 더 이상 없습니다. 정형 읽기 도구 12종 `ledger_get`, `ledger_defect`, `ledger_task`, `ledger_history`, `ledger_search`, `ledger_defects`, `ledger_tasks`, `ledger_conditions`, `ledger_attention`, `ledger_stats`, `ledger_projects`, `ledger_codes`가 이를 대체합니다. 스키마를 직접 읽던 질의에는 대응하는 도구가 없습니다.
3. **`_hostAttestation`의 값이 바뀌었습니다.** 키는 그대로입니다. `<vendor>:<session-id>`만 있는 값은 `ATTESTATION_UNSIGNED`로, `pgla1` 토큰은 `ATTESTATION_VERSION_UNSUPPORTED`로 거절됩니다. 새 값은 `pgla2.<author>.<tool>.<request id>.<arguments digest>.<issued at>.<signature>`이며, 인자의 RFC 8785 정규형의 SHA-256까지 덮는 Ed25519 서명입니다. 새 훅 jar만 이 값을 만듭니다.
4. **기존 부여에는 세션 키가 필요합니다.** `import-legacy`는 옛 부여를 키 없이 복사하므로, 소유자가 `key-register`로 세션 키를 등록하기 전까지 가져온 작성자의 쓰기는 `ATTESTATION_SIGNATURE_INVALID`로 거절됩니다. 등록하면 그 부여는 이전처럼 동작합니다.
5. **가져온 영수증은 재생하지 않습니다.** 1.x 요청의 `request_id`를 반복하는 쓰기는 `REQUEST_ID_LEGACY`로 거절되므로 새 요청 ID를 사용해야 합니다.
6. **설정이 옮겨졌습니다.** 1.x의 환경 파일은 없어졌습니다. 비밀은 `secret-set`으로 저장하고, 배포 설정은 README에 나열한 Spring Boot 속성입니다.

### 이전 절차

1. 먼저 모든 클라이언트 호스트에 훅 jar를 설치하고 `PATH`에 Java 25 런타임을 둡니다. 서명하는 훅이 없는 쓰기는 `HOST_ATTESTATION_REQUIRED`로 거절됩니다.
2. DBMS의 도구로 데이터베이스 계정 둘(앱 계정과 DDL 계정)을 만들고, JDBC 드라이버를 직접 구한 뒤, 호스트의 설치기로 2.0.0 jar를 설치합니다. 1.x 스키마는
   변경하지 않고 읽기만 합니다. 설치기가 비밀을 저장하고(`secret-set`, `token-generate`), 드라이버를 등록하고, `migrate`로 스키마를 만들고, `dml-grants.sql`을 앱 계정에
   적용하고, 두 서비스를 시작합니다. 세 대상(개인 PC, Windows 서버, Linux 서버)은 README(설치)에 설명되어 있습니다.

```sh
sudo deploy/install.sh --jars=dist --driver-jar=<driver-jar> --driver-class=<driver-class> --owner-account=<ddl-account> --app-account=<app-account> --jdbc-url=<jdbc-url>
```

```bat
deploy\install.cmd dist <winsw-exe> <driver-jar> <driver-class> <ddl-account> <app-account> "<jdbc-url>"
```

3. 1.x 호스트에서는 이 순서로 이전합니다. DBMS의 덤프 도구로 장부 데이터베이스를 백업하고 `/etc/pg-ledger-mcp`(1.x 파일 `/etc/pg-ledger-mcp/env`에 1.x의
   비밀이 있습니다)와 1.x 유닛 파일을 복사해 둡니다. 1.x 서비스는 직접 멈춥니다(기본 이름이면 `sudo systemctl stop pg-ledger-mcp pg-ledger-mcp-admin`이며, 설치기는
   1.x의 어떤 것도 멈추지 않습니다). 데이터베이스 계정 둘을 만든 뒤 `--from-1x-env=<file>`과 함께 설치하면 어떤 토큰이든 만들기 전에 1.x의 토큰을 옮겨 오므로 클라이언트와
   관리 웹 로그인이 그대로 동작하며, 값은 출력하지 않고 이미 있는 비밀은 그대로 둡니다. 새 유닛이 대체하는 1.x의 유닛 파일은 `<file>.1x-backup`으로 보관합니다. 터미널이 없으면
   `--stdin`을 더하고 비밀번호를 표준 입력으로 줍니다.

```sh
sudo deploy/install.sh --jars=dist --driver-jar=<driver-jar> --driver-class=<driver-class> --owner-account=<ddl-account> --app-account=<app-account> --jdbc-url=<jdbc-url> --from-1x-env=/etc/pg-ledger-mcp/env
```

| 1.x 환경 값 | 2.0.0 비밀 |
|---|---|
| `DBHUB_AUTH_TOKEN` | `ledger.mcp.token`이며, 같은 값을 `ledger.admin.agent-token`에도 사용합니다 |
| `PGLEDGER_ADMIN_TOKEN` | `ledger.admin.token`. 1.0.0 설치에는 관리 웹이 없어 이 값도 없으며, 그 경우 새 토큰을 생성하여 한 번 보여 줍니다 |
| 장부 로그인의 데이터베이스 비밀번호 | `ledger.jdbc.password`이며, 설치기가 앱 계정의 것을 입력받습니다 |

4. `migrate`와 `setup`이 만든 스키마(`setup`을 실행하는 설치기를 마친 상태)에 1.x 장부를 한 번 가져옵니다. 가져오기는 1.x 스키마를 읽기 전용으로 읽어 모든 행을 한 트랜잭션으로 복사하고, 모든 표의 행 수와 SHA-256 다이제스트를 대조합니다. `--verify-only`는 대조만 다시 합니다. `setup`이 쓴 시드 코드와 감사 행은 받아들이고(1.x에도 있는 시드 코드는 1.x의 값을 따릅니다), 원장 데이터 표, 세션 키, 이전 가져오기 중 하나라도 이미 있으면 거부하며, 새 스키마가 담을 수 없는 값(공백이 있는 ID, 대소문자만 다른 ID 쌍, 칸보다 긴 텍스트)은 아무것도 쓰지 않은 채 모두 나열합니다. 해당 행을 1.x 장부에서 고친 뒤 다시 실행합니다. 1.x의 ID는 그대로 유지합니다. 작업이나 조건의 ID는 공백과 제어 문자가 없는 1자 이상 120자 이하이면 대소문자와 문자 종류(`:`, `/`, `#`, `.`, `_`, `-` 등)를 가리지 않으며, 결함 ID는 기존 형식(`<CODE>-D-0001`)을 그대로 씁니다. 같은 종류에서 대소문자만 다른 ID는 새 스키마에서 하나의 ID이므로(조회는 ID를 정확히 비교하고, ID를 대문자로 바꾼 키는 어떤 DBMS에서도 유일합니다) 가져오기는 그런 쌍을 거부하며, 작업이나 조건을 이미 있는 ID와 대소문자만 다르게 만들 수도 없습니다(`DUPLICATE_KEY`). 1.x의 빈 문자열(`purpose`, `success_condition`, `behavior`, `root_cause`, `condition_text`는 `''`를 허용했습니다)은 NULL로 저장하고 도구는 1.x처럼 빈 문자열을 돌려줍니다. 조건의 `code`(200자)와 `ci_ref`(2000자)는 이전 2.0 빌드보다 길어졌고, 작업의 `origin_ref`는 긴 텍스트(쓸 때 20000자까지)여서 1.x의 모든 값이 들어갑니다. 도구의 입력 키는 바뀌지 않았고 어떤 도구 스키마에도 ID의 패턴이 없습니다.

```sh
java -jar ledger-cli.jar secret-set ledger.import.source.password
java -jar ledger-cli.jar import-legacy --owner-account=<ddl-account> --ledger.import.source.url=<jdbc-url> --ledger.import.source.username=<account>
```

5. 모든 작성자가 세션 키를 등록합니다. 세션이 공개 키와 지문을 출력하면, 소유자가 지문을 대조한 뒤 그 키가 만들어진 서버에 키를 등록하고, 그 작성자의 부여가 동작합니다.

```sh
java -jar ledger-client-hook.jar session-key <server> <author>
java -jar ledger-cli.jar key-register <author> <public-key-or-block> <fingerprint>
```

6. 클라이언트를 전환합니다. `execute_sql_reader`와 `search_objects_reader` 호출을 읽기 도구로 바꾸고, 쓰기 결과의 키는 결과 자체에서 읽습니다. `mcp-check`와 `import-legacy --verify-only`로 서버를 확인합니다.
7. 되돌리려면 2.0.0 서비스를 멈추고, `<file>.1x-backup` 유닛 파일을 복사해 되돌리고(백업은 그대로 남습니다), `sudo systemctl daemon-reload`를 실행한 뒤 1.x 서비스를 이전 설정으로 시작합니다. 가져오기는 1.x 스키마를 변경하지 않습니다. 이후 설치기를 다시 실행하면 자리의 유닛과 같은 백업은 그대로 두고, 내용이 다른 백업은 `prepare-host`를 두 파일을 밝힌 `HOST_FAILED`로 멈춥니다.

### 추가

- 정형 읽기 도구 12종. 목록 도구에는 `max_rows`, `cursor`, `truncated`, `next_cursor`가 있습니다.
- `notifications/tools/list_changed`: 공통코드가 바뀌면 연결된 클라이언트가 재시작 없이 반영합니다.
- 이력이 바뀌기 전의 전체 행을 보관합니다(`before_data`, `include_before`를 주면 반환됩니다).
- 작업 ID를 주지 않으면 서버가 부여합니다.
- Claude Code, Codex, Antigravity가 함께 쓰는 훅 jar `ledger-client-hook.jar`(`clients/claude`, `clients/codex`, `clients/antigravity`)와 Ed25519 세션 키.
- 관리 웹은 서버 렌더링이며, 관리 토큰 또는 OpenID Connect(`ledger.admin.oidc.owners`)로 로그인하고 JDBC 드라이버를 등록합니다(`ledger.admin.driver-directory`).
- 명령 20개를 가진 `ledger-cli`. `driver-register`, `migrate`, `import-legacy`, `key-register`, `key-revoke`, `mcp-check`, `token-generate`, `secret-import-1x`, `render-deploy`, `prepare-host`, `seal-host` 등이 있습니다. `secret-set`, `migrate`, `import-legacy`는 `--stdin`을 받고(`docker login --password-stdin`의 관례: 비밀은 표준 입력의 첫 줄이며 인수나 환경 변수로는 받지 않습니다), `secret-set`은 `--if-absent`를, `token-generate`는 `--copy-to=<name>`을 받으며, `secret-import-1x`는 1.x 환경 파일의 토큰 두 개를 비밀 저장소로 옮깁니다.
- `prepare-host`와 `seal-host`는 설치기가 운영체제 명령(`install -d`, `install -m`, `mkdir`, `icacls`, `copy`)으로 하던 일을 Java로 합니다. 소유자·모드 또는 ACL을 가진 폴더, jar·드라이버·WinSW의 복사, 비밀을 LocalService에 넘기는 일입니다.
- Java가 할 수 없는 것(`useradd`, `runuser`, `systemctl`, WinSW, `sc.exe`, `nginx`)만 직접 실행하고 나머지는 `ledger-cli`에 맡기는 설치기 두 개: `deploy/install.sh`(Linux, systemd, 선택적 nginx 사이트)와 `deploy\install.cmd`(Windows, WinSW로 서비스 등록). 개인 PC, Windows 서버, Linux 서버를 다루며 macOS는 지원하지 않습니다. `--name=<name>`은 자기 인스턴스를 만듭니다. 서비스는 `<name>`과 `<name>-admin`이고, Linux 사용자, 디렉터리, WinSW id가 이름을 따르므로 인스턴스 둘(또는 아직 1.x가 도는 호스트 옆의 인스턴스)을 각자의 포트로 한 호스트에 둘 수 있으며, Java가 무엇이든 만들기 전에 이름을 검증합니다. 두 서버는 어떤 사람에게도 속하지 않는 서비스 계정 하나(Linux는 `pg-ledger-mcp`, Windows는 LocalService)로 실행하며, 비밀 디렉터리는 그 계정만 읽을 수 있습니다.
- 데이터베이스 계정 둘: 앱 계정에는 `migrate --app-account=<account>`가 `dml-grants.sql`의 최소 권한(ANSI `GRANT`만, DDL 없음, 이력에 `UPDATE`와 `DELETE` 없음)을 부여하고, DDL 계정은 `migrate --owner-account=<account>`에 쓰며 그 비밀번호는 숨김 입력으로 받고 저장하지 않습니다.
- 설치의 설정은 한 디렉터리(`ledger.secrets.home`)에 있습니다. 설치기가 렌더하는 `application.yaml`과 서비스별 파일 하나씩, 그리고 운영자의 설정을 위한 `local.yaml`(교체하지 않습니다)입니다.
- `token-generate`는 bearer 토큰과 관리 토큰을 `SecureRandom`의 32바이트로 만들고, 다시 실행해도 이미 있는 토큰은 유지합니다.
- 스키마 파일 `V{n}__*.sql`과 이력 표 `schema_history`를 `migrate`가 적용하며, 바뀐 파일이 있으면 모든 프로세스가 시작할 때 멈춥니다.
- 장부 데이터베이스의 첫 설정 `setup`: `migrate`처럼 마이그레이션하고, 앱 계정이 스키마를 쓸 수 있는지 확인하며(쓸 수 없으면 종료 코드 `3`과 빠진 단계를 알림), 없는 시드 코드를 `code-set`이 쓰는 서비스로 추가하고, 시드와 데이터베이스를 개수와 SHA-256 다이제스트로 대조합니다. 다시 실행해도 아무것도 바뀌지 않습니다. 설치기가 호출합니다.
- `ledger-cli.jar` 안의 시드 번들 `ledger-seed.mv.db`: 빌드가 `src/seed/defect-categories.tsv`와 `src/seed/install-defaults.properties`에서 만들며(모듈 `ledger-seed`), 기본 결함 분류 14개와 설치 기본값이 들어 있습니다. H2 데이터일 뿐이며, 장부는 언제나 운영자가 설치한 데이터베이스 시스템에 저장되고 H2 드라이버나 H2의 JDBC URL의 등록은 거절됩니다. H2 드라이버는 `ledger-cli`만 가지며, MCP 서버와 관리 웹에는 없습니다.
- `install-default <name>`: 설치 기본값(`instance-name`, `mcp-port`, `admin-port`)은 시드 번들에 한 번만 적고, `render-deploy`, `prepare-host`, `seal-host`, `mcp-check`와 두 설치기가 거기서 가져옵니다.
- Linux 서버의 자동 TLS 인증서: `ledger-cli`의 `tls-issue`와 `tls-renew`는 표준 ACME 클라이언트(RFC 8555, HTTP-01, 라이브러리 acme4j(Apache-2.0)로 구현)이며 `fullchain.pem`과 `privkey.pem`(표준 PEM)을 `/etc/<name>/tls`에 씁니다. `render-deploy`와 `prepare-host`는 `--tls-certificate`와 `--tls-key` 대신 `--tls-acme`를 받으며, `--acme-directory=<url>`(기본값은 Let's Encrypt의 운영 디렉터리)과, 설치기에는 `--acme-email=<address>`와 `--agree-tos`도 있습니다. 그러면 nginx 사이트에는 자기 호스트 이름마다 80 포트 블록(증명, https로 리다이렉트)과 443 블록이 들어가고 `default_server`는 차지하지 않으며, systemd 서비스와 타이머가 인증서를 갱신합니다. 운영자의 인증서(`--tls-certificate`, `--tls-key`)는 그대로입니다.
- 배포 설정: `ledger.admin.agent-token`은 필수이며 `ledger.admin.token`과 달라야 하고, `ledger.admin.lockout.global-delay`는 많은 클라이언트가 실패할 때 토큰 확인을 늦춥니다.

### 변경

- PostgreSQL 함수와 트리거가 강제하던 규칙(부여, 상태 전이, 같은 세션 거절, 영수증, ID 부여, 생성 출처)은 같은 오류 토큰으로 응용 서비스가 강제합니다.
- 애플리케이션에는 이력을 수정하거나 삭제하는 경로가 없으며, 데이터베이스 모듈의 부여 템플릿(`dml-grants.sql`)은 애플리케이션 계정에 이력의 `UPDATE`와 `DELETE`를 주지 않습니다.
- 시각은 모든 곳에서 UTC이며, 관리 웹은 브라우저의 지역 시각으로 표시합니다.

MIT License는 이미 그 라이선스로 공개한 사본, 곧 v1.0.0과 v1.1.0에만 계속 적용합니다. 제13조에 따라, 수정한 버전을 네트워크 서비스로 운영하는 자는 그 이용자에게 해당 소스 코드를 제공해야 합니다. 관리 웹은 각 페이지 하단에 소스 코드 링크를 보여 주며, 그 주소는 설정 `ledger.source.url`(기본값은 프로젝트의 공개 저장소)입니다. 수정한 버전을 운영하는 자는 이 설정을 그 버전의 소스를 제공하는 곳으로 지정합니다.
- MCP 서버와 관리 웹은 서비스 계정 하나로 실행하며 root로는 실행하지 않습니다.
- 설치기는 이전에 `migrate`를 부르던 자리에서 `setup`을 부릅니다. 같은 옵션이면 `render-deploy`가 쓰는 파일은 바이트 단위로 같으며, 바뀐 것은 기본값을 두는 곳뿐입니다.

### 제거

- DBHub, Node, Node 훅 스크립트. Java 서버, Java 관리 웹, 훅 jar가 대체합니다.
- 1.x의 PostgreSQL 함수, 트리거, 로그인 역할. 작성자와 검토자 로그인은 이제 도구의 채널입니다.
- 도구 `execute_sql_reader`와 `search_objects_reader`.
- 비밀이 든 환경 파일. `deploy/`의 1.x 셸 설치 스크립트, 유닛 템플릿, 도메인 자동화는 설치기 두 개로 대체되어 제거되었으며, 저장소의 이력에 남아 있습니다.

### 보안

- 결함 D-0012를 수정했습니다. 1.x는 `_hostAttestation`을 검증하지 않아 bearer 토큰을 가진 쪽이 다른 세션의 이름으로 쓸 수 있었습니다. 이제 서버는 소유자가 작성자와 서버에 대해 등록한 키로 만든 Ed25519 서명을 검증하고, 도구, 요청 ID, 인자, 시각(`ledger.attestation.window`)을 확인합니다.
- 한 서버용 서명은 다른 서버에서 검증되지 않으며, 키가 없는 경우와 서명이 틀린 경우는 구별되지 않습니다.
- 관리 웹은 에이전트의 토큰을 거절하고(`AGENT_TOKEN_FORBIDDEN`), 실패한 시도를 제한하며(`ledger.admin.lockout.*`), CSRF 토큰과 `Secure`, `SameSite=Strict` 세션 쿠키를 사용합니다.
- 비밀은 숨김 입력으로 비밀 저장소에서 읽으며 출력하지 않습니다(토큰은 만들 때 `token-generate --print`가 한 번만 보여 줍니다). 비밀 디렉터리는 소유자 전용(POSIX 권한, Windows에서는 ACL)이며 서비스 계정만 읽을 수 있어, 장부의 비밀을 사람의 계정과 에이전트로부터 떼어 놓습니다.
- 자동 인증서의 키(`account.key`, `privkey.pem`)는 JDK로 만들고, 비밀 저장소의 보호 방식으로 소유자만 쓰도록 생성하며, 출력하지 않습니다. 인증서 파일은 원자적으로 교체하므로 갱신이 실패해도 이전 파일이 남습니다. 갱신 서비스는 서비스 사용자로 권한 없이 실행되어 TLS 디렉터리와 웹 루트만 쓰며, nginx는 고정된 명령 하나 `ExecStartPost=+/usr/bin/systemctl reload nginx`로 다시 읽게 합니다. 인증 기관의 챌린지 토큰은 base64url 문자로만 이루어졌을 때에만 파일로 씁니다.
- DDL 계정의 데이터베이스 비밀번호는 한 번의 실행을 위해 입력받으며 저장하지 않습니다. 앱 계정에는 DDL 권한이 없고 이력의 `UPDATE`와 `DELETE`도 없습니다.

### 요구 사항

- MCP 서버와 관리 웹의 호스트(서비스 계정도 실행하므로 모든 계정이 실행할 수 있는 경로, 즉 `/home` 아래가 아닌 곳이어야 하며, `deploy/install.sh`는 `--java=<path>`를 받아 이를 확인합니다), 그리고 훅 jar를 쓰는 모든 클라이언트 호스트에 Java 25 런타임이 필요합니다(클래스 파일 버전 69.0이며, 더 낮은 JVM은 `UnsupportedClassVersionError`로 거부합니다). 빌드에는 JDK 25가 필요합니다.
- 자동 인증서를 쓰려면 두 호스트 이름의 DNS 레코드가 서버를 가리키고 `80`과 `443` 포트가 nginx에 닿아야 합니다(앞에 CDN이나 프록시를 두면 `/.well-known/acme-challenge/`를 `80` 포트에서 캐시나 리다이렉트 없이 통과시키고 긴 연결을 유지해야 합니다).
- 사용자가 직접 구해 `driver-register`로 등록하는 JDBC 드라이버. 제품은 드라이버를 동봉하지 않습니다. 세션 시간대가 UTC인 데이터베이스.
- systemd가 있는 Linux, 또는 JDBC 드라이버처럼 직접 구하는 WinSW 2.x 실행 파일이 있는 Windows. 설치기는 아무것도 동봉하거나 내려받지 않습니다. nginx는 Linux 서버의 선택적 사이트에만 필요합니다.
- 1.x 장부는 마지막 설치 단계(관찰된 사례, 공통코드, 생성 출처)까지 완료되어 있어야 하며, 그렇지 않으면 `import-legacy`가 거부합니다.
- 클라이언트 호스트와 서버의 시계가 `ledger.attestation.window`(기본 5분) 안에서 맞아야 합니다.

### 알려진 제한

- macOS는 지원하지 않습니다.
- 행을 식별하는 텍스트(조건의 release나 code, 수정 기록의 저장소, 제목)가 1.x 장부에서 비어 있으면 NULL로 저장하지 않습니다. `import-legacy`가 그 행을 나열하고 아무것도 쓰지 않으므로 1.x 장부에서 고쳐야 합니다. 긴 텍스트 다섯 열의 빈 문자열은 가져옵니다(위 참조).
- `driver-register`는 장부 데이터베이스의 스키마가 아직 마이그레이션되지 않았을 때도(첫 설치, 또는 스키마를 지운 뒤의 재실행) 등록 파일을 쓰며, 소유자 감사 기록의 행은 아직 남지 않았다고 알립니다. 스키마가 준비되면 `migrate`와 `setup`이 그 행을 한 번 기록합니다.
- 자동 인증서는 nginx 사이트가 Linux용이므로 Linux에서만 쓸 수 있습니다. 명령 `tls-issue`와 `tls-renew`는 `--webroot`와 `--tls-dir`를 주면 어느 호스트에서나 실행됩니다.
- 스키마를 쓸 수 있는 권한은 데이터베이스 시스템의 문장이며 제품 SQL에 포함되지 않습니다. 앱 계정에 그 권한이 없으면 `setup`이 확인하고 종료 코드 `3`으로 멈춥니다. 운영자가 권한을 주면 `setup`이 멈춘 곳에서 이어집니다. `setup`은 이미 있는 코드를 바꾸지 않으므로, 이후 버전이 시드 코드를 바꿔도 기존 장부의 코드는 바뀌지 않습니다. 그럴 때는 `code-set`을 씁니다.
- `deploy\install.cmd`에는 `--stdin`과 `--from-1x-env`가 없습니다. Windows 설치는 대화형이며 1.x는 Linux에서만 실행되었습니다. 운영체제 사용자 생성, 그 사용자로 전환, 서비스 관리자, `nginx`는 Java에 해당 API가 없어 스크립트에 남습니다. 폴더 변경에는 root(Windows에서는 관리자 권한 프롬프트)가 필요하며 사전 점검은 없고, Java가 `HOST_FAILED`로 거부합니다.
- Windows에서는 설치 끝에 비밀을 서비스 계정에 넘기므로 그 뒤에는 `ledger-cli`의 소유자 명령이 비밀을 읽지 못합니다. 소유자 작업은 관리 웹의 화면에서 합니다.
- 같은 운영체제 사용자의 다른 프로세스는 세션 키 파일을 읽을 수 있으므로, 한 사용자 안의 격리에는 별도 계정이 필요합니다.
- 상승된 권한으로 실행한 훅은 거절됩니다(`WRONG_OWNER`). 호스트의 일반 사용자로 실행해야 합니다.
- 시간 창 안에서 다시 보낸 서명 토큰은 같은 호출을 반복할 수만 있고 다른 내용을 실을 수 없습니다. 이 창은 일회용 토큰이 아닙니다.
- MCP 서버, 관리 웹, 소유자 명령은 앱 계정 하나를 함께 쓰므로(서비스 계정은 비밀을 떼어 놓을 뿐 데이터베이스의 권한을 나누지 않습니다), 침해된 MCP 서버 프로세스는 세션 키와 부여도 쓸 수 있는 권한을 가집니다.
